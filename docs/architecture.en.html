vortexia · vortex-relay · v1

Two brokers, one relay, no direct line

Every Mac in the society runs its own local vortexia MQTT broker. Agents only ever talk to their own broker — the only thing that crosses machines is small JSON files, written and read through a relay neither Mac trusts the other to reach directly.

01 · Topology

Local broker, vortex-relay bridge, shared relay

ba-mac and uy-mac never open a socket to each other. A VortexRelayBridge on each side is the only thing that reads or writes the relay — local agents are unaware vortex-relay exists at all.

02 · Identification

Two entities, two structures

An agent is identified two independent ways, each answering a different question and feeding a different routing mechanism. Neither substitutes for the other.

Entity 1 · physical

Locator — where it runs

  • envName which machine — ba-mac, uy-mac
  • agentName which agent there — System
  • key agentName@envName — exact, single answer
Entity 2 · domain

Scope ladder — what it's for

  • rung 0 name — ≤34 chars, required
  • rung 1 short_description — ≤55 chars
  • rung 2 long_description — ≤89 chars
  • rung 3+ .vxia-scope.<N>.md — 144, 233, 377…
  • — README.md, ranked by its own length

03 · Routing

The address decides the path

AddressIdentity usedResolution
--to Robotics local registry, no envName needed direct MQTT publish on this broker
--to System@uy-mac physical locator resolveDirectoryName() — exact match or not-found
--scope "facturacion" domain scope text pickTargets() — similarity score, 0..N replies

04 · Directory

Built from what each environment says about itself

There's no central registry. Each environment periodically publishes both entities for its own roster to the relay, and periodically reads every environment's published snapshot back into one merged table — the only thing either routing path ever consults.

300s
publish own roster → directory-<env>.json
15s
read every environment's directory → merged table
1s
poll own outbox for incoming routed messages
